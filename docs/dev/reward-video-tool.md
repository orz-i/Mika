# 看广告领奖：把「真实播放」这条路做成工具

`reverse/qidian/VIDEO_TASK.md` 里比过四条路：真播自动化、故意让广告加载失败吃官方兜底、  
直连领奖接口、Hook 广告 SDK。只做第一条——它不伪造任何回调，用户看到的就是一次正常使用。

这个工具是 `phone_watch_reward_videos`，实现是 `PhoneWatchRewardVideos`，  
纯逻辑（读接口、算下一步）在 `RewardTaskPlan`。

## 1. 为什么不直接用 `phone_run`

`phone_run` 已经能按文字点、按条件等，但它按「遇到看不清就停」的思路做，碰到广告会卡在三个地方：

- **广告没有固定长度**：15 秒、30 秒、「5 秒后可跳过」都有，写死 `wait` 不是早就是晚；
- **中途有跳过**：激励视频播到一半会出现「跳过」，这时候点掉奖励就没了，得等够时间再点；
- **网页里的文字点不动**：福利中心是 WebView，文字节点常常没有可点击的编号，只有位置。  
  只按编号点会一直点不动（真机上就踩过：`去完成` 和任务格都点没反应，日志一条广告都没有）。

所以专门做了一个工具，把这三件事包进去。

## 2. 每轮做什么

```
轮次开始
 ├─ 从第二轮起看一眼任务接口（抓包开着才有）→ 今天走完了就停；第一轮不看，
 │   那一刻抓到的 `mainPage` 可能是几分钟前甚至昨天的
 ├─ 找领奖按钮 → 有就点掉，**这一轮到此为止**（先把已达成的阶梯领完，别堆着）
 ├─ 找任务入口 → 点它，把广告叫出来
 ├─ 等这次广告（`watch`）
 │   ├─ 任务入口从屏上消失 = 广告盖上来
 │   ├─ 等正片放完（`VIDEO_POLLS` ≈ 15.6 秒）
 │   ├─ 点 CTA → 优先认跳转确认框/授权框，在框上耗掉时长后按「取消」；
 │   │   真被拉出去了才按返回，不进对方界面
 │   ├─ 一直没有广告 → `ad_not_shown`，停
 │   └─ 关不掉 → `ad_timeout`，停
 ├─ 关掉广告、退回网页 → `watched` 加一，奖励留到下一轮开头领
 └─ 抓包开着时读一次 `finishWatch` 的 `Data.RewardList`，非空才算这阶真发下来了
```

**一轮只做一件事**：领奖、点入口、等广告，谁先命中谁结束这一轮。所以九阶走完最多需要
9 次广告 + 9 次收下 = 18 轮，`rounds` 给 9 只能走到一半（见 §4）。

停下来的原因会写在结果的 `stopped` 里：`round_limit`、`done`、`task_not_found`、  
`ad_not_shown`、`ad_timeout`、`tap_failed`、`nothing_to_watch`。

## 3. 判定口径

| 要判的事     | 用什么                                                                          | 为什么不用屏幕      |
| -------- | ---------------------------------------------------------------------------- | ------------ |
| 今天还剩几阶   | `mainPage` 的 `DailyBenefitModule.Process` 与 `DailyBenefitModule.TaskList` 长度 | 进度条和格子只是展示   |
| 这一阶发没发下来 | `finishWatch` 响应里的 `Data.RewardList`                                         | 广告关掉不等于算数    |
| 有没有可领的奖  | `TaskList[i].IsFinished=1 && IsReceived=0`                                   | 格子上的勾可能是上一阶的 |
| 广告播完没有   | 领奖按钮出现                                                                       | 倒计时读不到       |

接口读不到（抓包没开、响应过期）时**不猜**：`apiState` 返回 null，整个流程退回按屏幕走，  
结果里也不写 `apiProcess` 这几个字段，免得把「没读到」当成「值是 0」。

## 4. 参数

| 参数          | 默认                    | 说明                              |
| ----------- | --------------------- | ------------------------------- |
| `taskText`  | 空                     | 任务入口上的文字，逗号分隔。为空时只领已经达成的奖，不点新任务 |
| `claimText` | `领取,立即领奖,知道了,开心收下,确定` | 领奖/收下按钮的文字                      |
| `rounds`    | 9                     | 最多走几轮，上限 20。一轮只做一件事，走完九阶要给 18（见本节末） |

「等广告放完」和「等跳转停留」都没有做成参数，都写成常量（`VIDEO_POLLS`、`BROWSE_POLLS`，  
各 13 次 × 1.2 秒 ≈ 15.6 秒）：它们是规矩不是偏好。激励视频点早了奖励就没了，  
这个值调小了就是在帮倒忙。

起点福利中心的调用大致是：

```json
{"taskText":"惊喜礼包,10点章节卡,10-3点订阅券","rounds":18}
```

`rounds` 给 18 而不是默认 9：**一轮只做一件事**。看一次广告占一轮，领一次奖（含关掉
「恭喜获得」弹层）也占一轮，真机 trace 就是 `watch → claim → watch` 交替。九阶走完
最坏是 9 次广告 + 9 次收下 = 18 轮；给 9 会在一半停成 `round_limit`。上限 20，
起始就有好几阶待领时可以给到 20。

## 5. 提示词怎么写

工具进来之后的九轮不需要模型操心，提示词只要交代三件事：**让它到位、把屏上的字告诉它、
然后别插手**。下面两段可以直接抄。

### 5.1 接手现场

Mika 自己那块屏已经停在福利中心时，最短的一段：

```text
现在屏上是起点读书的「福利中心」，有「激励任务」一列阶梯（惊喜礼包、10点章节卡、10-3点订阅券）。

直接调用 phone_watch_reward_videos，参数：
{"taskText":"惊喜礼包,10点章节卡,10-3点订阅券","rounds":18}

不要先用 phone_run 自己点。跑完把返回的 JSON 原样贴出来。
```

### 5.2 从冷启动

让它自己走过去：

```text
打开起点读书，进「我的 → 福利中心」，滚到有「激励任务」阶梯、右侧带「去完成」的那一屏。

到位后先 phone_observe 一次，把阶梯上那几个奖励名字原样抄下来，
然后一次性调用 phone_watch_reward_videos：
{"taskText":"<你抄下来的名字，逗号分隔>","rounds":18}

规则：
1. 广告会跳微信、或者弹授权框。你不要替它点「打开」「允许」「确定」，也不要自己进微信去逛；
   工具会停在框上按取消，或只按一次返回。
2. 整个过程可能 3~5 分钟，中途不要换招、不要手动补点。
3. 跑完报告 watched / claimed / stopped；开了抓包再报 apiProcess 和 apiTotal。
4. stopped 是 task_not_found，说明没进到那一屏，把屏上文字列出来，不要盲点。
5. 只有 ad_not_shown 或 tap_failed 允许再调一次；连续两次失败就停，别把当天的失败次数耗光。
```

第 1 条「到位」最容易漏：Mika 跑在自己的虚拟屏上。用户在物理屏上把起点打开到福利中心，
它那边是空的——真机上第一次就是这个现象，`taps=0`、`task_not_found`。

### 5.3 让它把验收一起带回来

```text
跑完之后再读一次 mainPage：Data.DailyBenefitModule 的 Process 要等于 TaskList 的条数。
不相等就再调一次 phone_watch_reward_videos（rounds 给 4）把剩下的补上，最多补两次。
```

三个数对得上才算真的到账：`watched` 是工具自己数的，`verifiedRewards` 是抓包里
`finishWatch` 的 `Data.RewardList` 条数，`apiProcess` 是接口侧进度。后两个要打开
设置里的「网络抓包」才有；关着也能跑，只是结果里没有这几个字段。

### 5.4 写错了会怎样

| 提示词里写的              | 实际发生                     | 怎么改                            |
| ------------------- | ------------------------ | ------------------------------ |
| 「帮我领一下福利」           | `task_not_found`，屏上什么都没匹配到 | 把阶梯上的奖励名字写进 `taskText`         |
| 「每个格子都点一遍」          | 点到的是标签，页面不动，`ad_not_shown` | 不要逐个点，交给工具，它自己会退到右侧「去完成」       |
| 「我已经在福利中心了，你直接跑」    | 它虚拟屏是空的，`taps=0`         | 明确让它自己打开并走到那一屏                 |
| 不给 `rounds`         | 默认 9，走一半停               | 给 18                           |
| 「看完点跳过/关闭就行」        | 提前关会弹「现在退出就没有奖励哦」，白跑一次   | 不用交代，工具按「点击浏览 15 秒」的规矩走        |
| 「跳微信了就点进去逛一下」       | 真进了微信，还会被引导授权            | 反过来交代：不进、不点、只按返回               |

一句话：提示词负责「到位 + 给词 + 报数」，广告怎么走完是工具的事，越少干预越稳。

## 6. 跳转确认框当成一次跳转

这批广告的奖励条件是「点击广告浏览 N 秒」，不是「看满 N 秒」。点了 CTA 之后有两条路，  
取决于广告主给的 deeplink 和机型：

| 现场   | 表现                                     | 怎么走              |
| ---- | -------------------------------------- | ---------------- |
| 有确认框 | 弹「即将打开微信」，`currentApp` 可能变也可能不变        | 停在框上耗掉时长 → 按「取消」 |
| 直达   | 没有框，`currentApp` 直接变成 `com.tencent.mm` | 在微信里待够时长 → 只按返回  |

**确认框那条更好**：框一出现广告那边就记上了跳转，而人还留在原地。

- 广告记到一次跳转点击，奖励照发；
- 一次跨 App 调用都没发生，微信不知道有人点过它，也就没有「唤起微信」这件事；
- 框上按的是「取消 / 不允许 / 拒绝 / 仅此一次」，不按「打开 / 允许」——  
  广告流程里没有理由给出去任何运行时权限。

**认框要早于认前台。** 有的系统上这个框画在起点自己的窗口里，`currentApp` 一直报起点，  
只有屏上的文字变了；只看前台会漏掉这一次跳转，接着去关广告，结果弹「现在退出就没有奖励哦」。  
所以点完 CTA 先查框（同一个屏上「取消」和「打开」都在才算框），再看前台。

**直达那条只能认了**：`currentApp` 变了、屏上没有框，这时已经进了对方 App。  
只按返回，不点对方的任何按钮、不授权、不读对方的界面，停留的几秒里对方最多记到一次唤起。  
三次返回还没回来就 `stuck_outside` 停下，不在别人家界面上继续点。

### 6.1 实测（PLK110，2026-11-21）

| 项      | 结果                                                                |
| ------ | ----------------------------------------------------------------- |
| 广告平台   | **优量汇**：前台是 `com.qq.e.tg.RewardvideoPortraitADActivity`，不是穿山甲     |
| 广告时长   | CTA 页写「点击后，看 15 秒可获得奖励」；`点击广告浏览 15 秒`                             |
| 跳转形态   | **两种都有**：同一轮里「立即购买」弹确认框、「去微信看看」直达 `com.tencent.mm/.ui.LauncherUI` |
| 任务入口   | 阶梯上那行「惊喜礼包」是标签，点了页面不动；真正叫出广告的是右侧「去完成」                             |
| 提前关会怎样 | 直接点 ✕，弹「现在退出就没有奖励哦 / 点击广告浏览 15 秒即可领取奖励」，两个键是「点击去浏览」「放弃奖励」         |

最终跑通的那一轮：

```json
{"ok":true,"watched":2,"claimed":1,"taps":10,"verifiedRewards":2,
 "stopped":"round_limit","apiProcess":3,"apiTotal":9,"apiClaimable":3}
```

- `watched=2` / `verifiedRewards=2`：抓包核到 `finishWatch` 的 `Data.RewardList` 一共 2 条，  
  服务端确实发了奖，不是「关掉广告自己以为看完了」；
- `apiProcess` 从 1 涨到 3：接口侧确认推进 2 阶，和 `watched` 对得上；
- 第 1 轮 `cta 立即购买 → dialog confirm → dismiss 取消`：**确认框路径**，人一步没进对方 App；
- 第 3 轮 `cta 去微信看看 → jump com.tencent.mm → back 1`：**直达路径**，只按了一次返回，  
  不在微信里点任何东西；
- 第 2 轮 `claim 知道了`：把「恭喜获得」弹层关掉，否则后面每一下都点在弹层外的遮罩上。

### 6.2 真机上踩到的三个坑

这三个都是写完单测仍然会中的，只有在真机上跑才暴露。

| 现象                                  | 根因                                                                                                | 修法                                           |
| ----------------------------------- | ------------------------------------------------------------------------------------------------- | -------------------------------------------- |
| `claimed=3`、`watched=0`，三轮全在点灰按钮    | 「已领取」里含「领取」，按文字模糊匹配每轮都命中它                                                                         | 点之前看元素自己的文字，含「已领」就排掉；同一块屏上点过的 `key` 也记住，不重复点 |
| `stopped=tap_failed`，广告已经叫出来了却停在第一步 | 脚本通道里 `phone_tap` 的纯坐标点击要能解析出「点到什么」，广告页无障碍树是空的（`treeQuality: unusable`），判 `target_unresolved` 直接拦 | 坐标点击改走 `phone_gesture`（路径手势，不做目标解析）          |
| 点击全部落在屏幕左上角，三次 CTA 一次没中             | `phone_observe` 的 `visibleText[].center` **本来就是 0-999 千分比**，又按 viewport 折算了一次                     | 直接用 `center`，不再折算                            |

还有一条不是 bug 但很关键：**CTA 位置不能写死**。同一批素材里「查看商品」在屏中部、  
「去微信看看」在底部、挽留页的「点击去浏览」在另一处，写死 `(500,800)` 只会戳到空白。  
现在先读屏上的字（`visibleText`），按「去浏览 / 去微信看看 / 查看商品 / 立即购买…」找中心点，  
读不到字才退回固定坐标。

## 7. 与另外两张图的关系

- **接口图谱**（`docs/dev/app-api-graph.md`）：提供「这个页面打哪个接口、返回什么字段」。  
  这里的 `RewardTaskPlan.readMainPage` 就是按那张图谱读 `Data.DailyBenefitModule`，  
  字段名不是猜的，是从真响应里核过的。
- **页面图谱**：提供「福利中心在哪、怎么进去」。工具本身只负责进去之后的九轮，  
  进去之前还是走正常的打开 App、点入口。

这个工具和图谱的分工是**两个方向**的，别搞混：

| | 谁负责 | 进图谱的是什么 |
| --- | --- | --- |
| 怎么走到福利中心 | 页面图谱（入口路径） | `首页 → 我的 → 福利中心` 这种**点击边**，跑一次学出来 |
| 到了福利中心做什么 | 本工具 | 不进边，只在这一页上记一条**能力**：`capabilities: ["phone_watch_reward_videos"]` |

把九阶流程做成图谱节点是行不通的：节点主键来自无障碍结构签名，WebView 页的签名每天都漂；
边也只能表达「点某个元素到某页」，装不下「看广告 → 等 15 秒 → 认框取消 → 领奖」。

反过来，**工具内部的子步也不能进图谱**。它们是 `Origin.Script`，以前会当成模型走的路去建边，
只是因为广告页读不到节点才一直没出事。现在 `AtlasLearner` 按 `source == "script"` 把子步挡在
结构之外（`event.parentTool` 说明是哪个工具发起的），只用它们给当前页记能力。
详见 `docs/dev/app-atlas-governance.md` 的「工具子步与页面能力」。

## 8. 真机上怎么验

1. 打开起点，进福利中心，停在「激励任务」被看见的那一屏；
2. 让 Mika 调一次下面这段（文字用屏上真实写的那几个，逗号分隔）：

   ```json
   {"taskText":"惊喜礼包","rounds":18}
   ```

   要一次走完当天的九阶，`rounds` 至少 18（九次广告 + 九次收下），见 §4 后面那段算术；
   只想验一次广告通不通就给 2，跑完 `stopped` 是 `round_limit` 属正常。
3. 看结果：`watched` 应该等于这次真看完的广告数，`claimed` 是领到手的奖励数；  
   抓包开着时 `verifiedRewards` 是 `finishWatch` 里 `Data.RewardList` 的条数之和；
4. 看 `rounds` 里这一轮走的是哪条：出现 `dialog` + `dismiss` 说明停在确认框上把时间耗掉、  
   按取消回来了，人没进微信；出现 `jump` + `back` 说明真跳出去过，那就得看是不是这批广告  
   没有确认框（有些 deeplink 直达的确实没有）；
5. 再看一次 `mainPage`：`Process` 应该涨了 `watched` 那么多。

如果 `stopped` 是 `task_not_found`，先确认那一屏真的露着任务格（要往上滑一点）；  
如果是 `ad_not_shown`，说明点了但广告没出来，多半是广告位没填充，这时候官方兜底会直接发奖，  
下一次调用用 `taskText` 留空、只领奖就行。

## 9. 不做什么

- 不伪造 `onRewardArrived`，不重放 `finishWatch`，不改广告 SDK；
- 不为了让广告加载失败去屏蔽广告域名——那是「故意制造失败以换奖励」，和真实播放不是一回事；
- 不点跳转框的「打开」，也不点授权框的「允许」；真的进到对方 App 只按返回，不读对方界面；
- 不做「无限重试」：广告连着两次不放就停，把当天的失败次数留给官方兜底。
